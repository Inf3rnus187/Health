# ADR 0004 — Metadata-driven initial migration

- Status: accepted
- Date: 2026-01

## Context

Alembic manages the **fixed** schema (§13). The models use PostgreSQL‑only
features (`JSONB`, dialect‑specific partial unique indexes) that Alembic's
autogenerate renders imperfectly, risking drift between models and migration.

## Decision

Each migration creates its **own named set of tables** from the ORM metadata
(`Base.metadata.create_all(tables=[...])` / `drop_all`). `0001_initial` owns
the baseline tables; `0002_ingest_mappings` owns just `ingest_mappings`, and
so on. A migration is thus always identical to the models for the tables it
owns, dialect‑specific types/indexes (JSONB, partial unique indexes) are
emitted correctly at run time, and — because each migration freezes its table
list — the chain stays **reproducible and incremental** (a new table does not
retroactively appear in the baseline).

Column‑level changes to an existing table still use ordinary autogenerated or
hand‑written `op.*` migrations — but, because the baseline is built from
**live** metadata, a fresh database already has any newly‑added column while
an older database does not. Such migrations must therefore be written
**idempotently**: guard each `add_column`/`create_index` on existence (via
`sa.inspect(op.get_bind())`). `0003_user_mfa` follows this pattern.

## Consequences

- Zero drift for the baseline; JSONB and partial indexes are correct on
  PostgreSQL and degrade cleanly to JSON on SQLite (used by the test suite).
- Tests build the schema via `create_all` directly, for speed.
- The **dynamic** schema (metrics) never needs a migration at all.
